# Agent Note: macOS V1 深海工作台

Status: implemented

[English](2026-08-14-macos-v1-deep-ocean-workbench.md) | 中文

## Problem

原生 macOS 客户端已经暴露 Harness 会话与交互协议，但如果各个 SwiftUI 页面独立实现，原生协议覆盖扩展后，列宽行为、输入区接管、状态颜色和控件会逐步分化。

## Decision

DS Harness macOS `0.1.1` 使用 [macOS 设计规范](../../../../apps/macos/DESIGN.md) 中的 V1“深海工作台”方案。SwiftUI 负责主窗口和设置场景、三栏布局、导航、对话时间线、输入区、交互接管、工具详情及响应式行为。AppKit 负责前台激活、应用生命周期、应用图标、原生目录选择器、Dock 徽标和通知导航。

主窗口使用浅色侧栏、居中的对话栏和可选的工具详情栏。侧栏与详情栏宽度在应用重启后保留。宽度不足时先关闭详情栏；低于 `1024 pt` 时，侧栏变为 `56 pt` 图标轨道。工具选择只在能够保留中央内容所需宽度时打开详情栏。

普通输入、审批和结构化问答共享一个稳定输入座位。交互接管期间，普通输入组件保持挂载，因此草稿不会丢失。审批卡和问答卡与输入卡使用相同最大宽度和状态语言。

设置使用独立原生窗口和固定导航栏。模型页通过 `credentials.set` 写入 DeepSeek API Key，通过 `credentials.describe` 读取状态，并且不会接收已存储的值。发行应用内置 Node 运行时和 Host sidecar，不开放 localhost 服务。

当前原生协议提供对话消息、工具展示数据、审批和结构化问答。客户端不会在相应协议方法出现前伪造运行轨迹、计划审阅、目标、后台任务、预设、插件或子智能体数据。

当目标会话没有显示在处于活跃状态的应用中时，应用会使用系统通知提醒轮次结束、审批请求和结构化问答。通知文字只包含通用状态，点击通知会打开对应会话。应用在第一条符合条件的通知准备投递时请求授权；没有实际功能需要时，不会增加相机、麦克风、屏幕录制、辅助功能或自动化 entitlement。

## Alternatives considered

**通过 WebView 嵌入 Web 客户端。** 这种方式可以更快复现浏览器界面，但会放弃原生窗口、菜单、焦点、辅助功能和桌面控件行为，也会把 Web 可执行 UI 与语义化原生协议混在一起。

**保留最小 SwiftUI 页面并由每个功能局部定样式。** 这种方式不需要共享布局组件，但协议覆盖扩展后，导航、状态、卡片和交互模式会产生差异。

**使用高对比度的 V2 深色侧栏。** 更强的色彩分割削弱安静的阅读表面，也不符合已确认的视觉方向。V1 的浅色侧栏和克制蓝青强调继续作为基线。

**预先申请所有可用的 macOS 权限。** 这种方式可以展示未来可能的集成，但会在没有当前产品操作需要时请求敏感访问，也会降低版本的可信度并增加审查难度。

## Consequences

原生客户端获得稳定的桌面信息架构，同时没有增加 WebView 或展示 RPC 方法。新的协议功能可以复用现有侧栏、标题区、输入座位、详情栏、设置导航和设计 token。长时间运行的任务可以提醒用户，同时不暴露对话内容，也不扩大应用的敏感权限。

首个版本在原生协议尚未提供结构化数据的功能上有意落后于 Web 客户端。浅色主题是 `0.1.1` 的验收目标；深色外观只保留系统派生的基本可用性。

Swift 和 Host 测试覆盖凭据状态、凭据单向写入、协议握手、交互解码和工具折叠。自包含应用冒烟验证使用内置 Node 运行时启动内置 sidecar。发布前仍必须完成渲染后的视觉比较，状态记录在[设计 QA 报告](../../../../apps/macos/design-qa.md)中。
